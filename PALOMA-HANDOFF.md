# Бриф: анализ Paloma и доработка продукта

Этот файл — контекст для Claude Code, запущенного **на Windows-ноутбуке, где установлена Paloma**.
Задача той машины: разобрать Paloma вживую и на основе разбора довести наш продукт
до состояния «как Paloma по функционалу для бань, но интерфейс лучше».

Здесь на Mac Paloma не установлена — поэтому живой разбор делается там, а решения
уже приняты с заказчиком и записаны ниже.

---

## 1. Что за проект

Мультитенантная SaaS ERP/POS для бань, саун и развлекательных центров (рынок — Казахстан,
KZT, фискализация ККМ/ОФД). Одна инсталляция обслуживает много независимых организаций
с изоляцией данных на уровне СУБД (RLS).

Стек: TypeScript, Fastify + PostgreSQL (`apps/api`), React 19 + Vite, shadcn/ui поверх
Radix (`apps/pos` — касса, `apps/owner` — кабинет владельца), доменное ядро в
`packages/core` (деньги, время, тарификация).

Как запустить и проверить — в [README.md](README.md). Нужен Node 22.6+ и PostgreSQL 14+.
На Windows PostgreSQL проще всего поставить через официальный установщик EDB или Docker.

Уже написанные документы, прочитать перед работой:
- [docs/gotovnost.html](docs/gotovnost.html) — что готово, что блокирует запуск (свежий срез)
- [docs/plan-v2.html](docs/plan-v2.html) — сравнение с Paloma по пунктам
- [docs/tz-mvp.html](docs/tz-mvp.html) — техзадание
- В памяти проекта (`~/.claude/.../memory/`) — концепция продукта, UX-приоритеты,
  правила учёта наличных, требование использовать только shadcn/ui и токены цвета.

## 2. Что уже работает (проверено тестами, ~116 тестов)

Касса: привязка устройства + вход по PIN, смены и Z-отчёт, приём гостя и таймер от
серверного времени, посегментная тарификация через границу тарифа, товары/продления/оплата
(наличные, карта, смешанная, возврат), работа без интернета с идемпотентной очередью.

Бронирование: шахматка, непересечение через `EXCLUDE` в PostgreSQL с буфером уборки.

Абонементы: посещения/часы/безлимит, баланс как свёртка append-only леджера, заморозка,
подсказка на кассе.

Кабинет владельца: справочники (абонементы, услуги с тарифами, помещения, товары,
сотрудники, настройки филиала), отчёты (выручка, средний чек, загрузка, смены с
расхождениями, долг по абонементам), светлая/тёмная темы.

Роли **реально работают** — `apps/api/src/auth.ts`, `ROLE_PERMISSIONS` + проверки `can()`
в каждом роуте: `owner` (всё), `manager` (смена, визиты, оплаты, отчёты, возвраты),
`cashier` (смена, визиты, оплаты, брони, продажа/списание абонемента), `accountant`
(только отчёты). Проблема — их не видно и не объяснено в интерфейсе.

## 3. Что блокирует полный запуск

Жёсткие блокираторы (без них клиента подключить нельзя):
1. **Фискализация ОФД** — в коде нет ничего, включая интерфейс `FiscalDevice` (проверено
   11.09.2026; ранее ошибочно считалось, что интерфейс заложен). Ждёт выбора оператора
   заказчиком (Webkassa / re:Kassa / Nurkassa / …).
2. **Печать чека** (ESC/POS термопринтер) — в одном блоке с фискализацией.
3. **Нет сервера** — Docker, домен, HTTPS, бэкапы, размещение в РК.

Дыры в безопасности (закрыть до боевой работы):
- `apps/api/src/auth.ts` — `JWT_SECRET` по умолчанию `dev-secret-change-me`. Нужен запрет
  старта сервера с дефолтным секретом.
- PIN 4 цифры без лимита попыток — нужен rate limit.
- `apps/api/src/routes/orders.ts` — маршрут возврата не вызывает `can()`, глобальной проверки
  прав нет. Кассир и бухгалтер могут оформить возврат, хотя по модели ролей это право
  управляющего (найдено при разборе Paloma 11.09.2026).

## 4. Стратегическое решение (принято с заказчиком)

**Paloma — ориентир по объёму функций и потокам, ядро остаётся своё.** Не переписываем.
По банной специфике (посегментный расчёт, брони с буфером уборки, абонементы-леджер, RLS)
мы уже сильнее Paloma — она универсальная система, бани для неё одно из направлений.
Отстаём по складу с себестоимостью, фискализации, мобильному приложению.

Значит работа = «дозакрыть дыры + переработать интерфейс», а не клонировать код Paloma.

## 5. Две модели бань (решение: поддержать обе, переключателем)

Разбор рынка показал два разных бизнеса под одним словом:

- **Модель А — частная сауна / комплекс.** Цена за зал по часам, минимум обычно 2 часа,
  разные цены по дням/времени, **доплата за гостей сверх включённых** («до 6 человек в
  цене, каждый следующий +1500 ₸/час»). Абонементов почти нет, вместо них депозит.
- **Модель Б — общественная баня / термы.** Цена за человека (входной билет), льготные
  категории (дети, пенсионеры), абонементы на 4/8/10/15/30/60 посещений — обычное дело.

**Дыра, которую надо закрыть в первую очередь:** сейчас число гостей записывается, но в
расчёте не участвует. Заведение Модели А теряет ~9000 ₸ с обычного вечера пятницы.

**Как поддержать обе, не двоя продукт:** расширяем модель услуг, а не разветвляем домен.
- У услуги есть `kind`: `time_based` (зал) и `extra` (штучное).
- К тарифам `time_based` добавляем два поля: **включено гостей** и **доплата за гостя/час**.
- Добавляем третий `kind`: **`per_person`** — входной билет, те же правила по дням/времени.
- **Категории гостей** (взрослый / ребёнок / пенсионер) — справочник организации,
  действует на `per_person`.
- «Тип заведения» в настройках — это **пресет** (подставляет дефолты, прячет ненужные
  разделы вроде абонементов для частной сауны), а НЕ жёсткая ветка. Заведение может иметь
  и зал, и общее отделение одновременно.

Полный разбор рынка с цифрами — артефакт «Две бани, две модели цен»
(https://claude.ai/code/artifact/ec0aa332-11b9-4ecd-a801-ba475cabee00).

## 5а. Что показал живой разбор Paloma (11.09.2026)

Полный аудит — [docs/paloma-razbor.md](docs/paloma-razbor.md), скриншоты — [docs/paloma/](docs/paloma/).
Здесь только то, что меняет план.

- **Доплаты за гостей нет и у Paloma.** Число гостей в счёте есть, в тарифе — нет. Фаза 1
  остаётся: это не догоняние, а преимущество.
- **`categoryid` в «временных ценах» Paloma — категория товара**, не категория гостя
  (документация: справочник «Категория» — для аналитики товаров). Льготных категорий
  гостей в Paloma нет. Фаза 2 (категории гостей) — наша собственная идея, не копия.
- **`per_person` и `entry` у нас уже объявлены** в `services.kind` (миграция 002), но в
  расчёте, API и интерфейсах не используются. Фаза 2 — довести, а не заводить с нуля.
- **Депозит и «в долг» — штатные виды оплаты** в форме оплаты Paloma (в демо выключены).
  Для частных саун (Модель А) депозит нужен — кандидат после Фазы 2.
- **Возврат в Paloma невозможен без пароля**, заданного владельцем в кабинете. У нас
  `POST /v1/orders/:id/refunds` вообще не проверяет права — возврат может оформить любая
  роль. Добавлено в Фазу 0.
- **Смену нельзя закрыть с неоплаченными счетами.** Сама смена при этом может висеть
  открытой днями — Paloma это не ограничивает.
- **Интерфейсы Paloma — наборы прав на одном плане столов**: тарификатор (запуск времени,
  журнал), официант (счета без денег), кассир (деньги, смена, возвраты), режим продаж
  (быстрый чек с оплатой). Для нашего экрана «Роли и доступ» — готовая модель.
- **Журнал Paloma слабее нашего бронирования**: бронь на стол, где сейчас открыт счёт,
  сохраняется; статусов брони, гостей и предоплаты у записи нет; форма модальная и
  блокирует весь фронт, если оказалась под другим окном.
- **Фронт синхронизируется с облаком** каждые несколько минут. Тестовые записи разбора
  (клиент «TEST Claude», бронь 11.09 15:00 на «Стол 1», пустой счёт №2 на «Стол 2»)
  попали в демо-аккаунт — их стоит удалить в кабинете Paloma.

## 6. План работ по фазам

Порядок согласован с заказчиком.

### Фаза 0 — быстрые правки интерфейса и безопасности
- **`MoneyInput`** — общий компонент поля суммы с разделением разрядов пробелом при вводе
  (`10 000`, не `10000`). Сейчас `formatTenge` группирует только при выводе; поля ввода
  (`форма.price` и т.п. в `apps/owner/src/Settings.tsx`) показывают сырьё. Заменить во всех
  формах цен в `apps/owner` и `apps/pos`.
- **Телефонная маска** — форматирование на лету в `apps/pos/src/Login.tsx` и в форме
  сотрудника. БД уже нормализует при сохранении (`db/migrations/011_phone_normalize.sql`) —
  нужен только UI-ввод в едином виде `+7 (7XX) XXX-XX-XX`.
- **Категории товара — select вместо ввода текстом.** Сейчас `p.category` — свободная
  строка (`Settings.tsx`). Сделать справочник категорий организации (или как минимум
  «уникальные существующие + добавить новую» комбобокс). Только shadcn/ui Select.
- **Экран «Роли и доступ»** в кабинете — матрица «роль × что может», показать что уже
  работает. Редактирование прав — позже, пока read-only.
- **Запрет дефолтного `JWT_SECRET`** — сервер не стартует в продакшене с
  `dev-secret-change-me`.
- **Лимит попыток PIN** — блокировка после N неудач.

### Фаза 1 — дыра в деньгах (обязательно)
- Тариф `time_based`: поля «включено гостей» + «доплата за гостя в час».
- Расчёт в `packages/core/src/pricing.ts`: цена зала за время + доплата за лишних гостей
  за то же время. Тесты в `packages/core/test/pricing.test.ts`.
- **Прозрачный разбор суммы на кассе до оплаты** — кассир и гость видят: сколько часов по
  какому тарифу, где граница тарифа, доплата за гостей, итог. Это и есть «хороший
  тарификатор» из запроса заказчика.

### Фаза 2 — Модель Б
- Новый `kind = per_person` (входной билет), правила по дням/времени как у `time_based`.
- Справочник **категорий гостей** организации (взрослый / ребёнок / пенсионер) со своей
  ценой или коэффициентом; льготы вроде «дети до 7 бесплатно».
- Экраны на кассе: выбор категории при приёме гостя, расчёт по числу людей.
- **Переключатель типа заведения** (пресет) в настройках филиала + скрытие раздела
  абонементов для частной сауны.

### Фаза 3 — филиалы
- Добавление филиала: `POST /v1/branches` (сейчас вкладка «Филиал» только редактирует
  существующие), форма с часовым поясом, переключение между филиалами в кабинете.
- Приоритет уточняется — зависит от того, есть ли у первых клиентов сети.

### Фаза 4 — блокираторы запуска (отдельный трек, ждёт решений заказчика)
- Интеграция с выбранным ОФД за интерфейсом `FiscalDevice`, очередь повторов, фискальный
  возврат, печать ESC/POS. Сборка программы для Windows (Tauri, каркас готов).
- Развёртывание: Docker + compose, HTTPS, домен, автоматические миграции при выкатке,
  ежедневные бэкапы с проверкой восстановления, мониторинг.

## 6а. Согласованный порядок работ до пилота (с 16.09.2026)

Фазы идут подряд, каждая — отдельный коммит с прогоном тестов. Порядок выбран так,
чтобы самая крупная и рискованная работа (филиалы) легла последней, когда остальное
уже стабильно. Фискализацию не трогаем: ждём от заказчика модель ККМ и способ выдачи
чека. Билет за человека, льготные категории, депозит, абонементы — не удаляем,
для первого клиента выключены настройкой.

| Фаза | Что | Зависит от | Риск для существующего |
|---|---|---|---|
| **Ф0** | Безопасность: право на возврат, лимит попыток PIN, запрет дефолтного `JWT_SECRET` | — | низкий, точечные правки |
| **Ф1** | Режим тарификации: «по времени входа» / «по сегментам», переключатель на услуге | Ф0 (общая база тестов) | **высокий** — трогаем `pricing.ts`; старый режим остаётся по умолчанию |
| **Ф2** | Внесение и изъятие наличных на кассе | Ф0 (права) | низкий, сервер уже умеет |
| **Ф3** | Скидка на кассе в пределах лимита кассира | Ф2 (общий экран денег), Ф0 (права) | средний — меняется итог заказа |
| **Ф4** | Перенос и отмена брони, неявка | — | средний — трогаем брони и `EXCLUDE` |
| **Ф5** | Мультифилиальность: создание филиала, сотрудники и права по филиалам, разрез отчётов | Ф0–Ф4 | **высокий** — трогает кабинет, отчёты и доступ |

После Ф5 отдельно возвращаемся к цене продукта: находка про 24 900 ₸ у Paloma и оплату
за каждое рабочее место меняет нашу тарифную модель, особенно на 3+ филиалах.

## 7. Задача для Claude на Windows-ноутбуке

> **Статус на 11.09.2026:** пункты 1–3 выполнены — Paloma разобрана вживую (фронт) и по
> файлам установки, аудит в [docs/paloma-razbor.md](docs/paloma-razbor.md). Не пройдены:
> облачный бэк-офис (нужен вход), расчёт времени и оплата на реальных суммах (в демо нет
> товаров и тарифов), возврат (нужен пароль). Пункт 4 — ждёт согласования. Код не менялся.

1. **Прочитать** этот файл, `README.md`, `docs/gotovnost.html`, `docs/plan-v2.html`,
   память проекта. Поднять проект локально, убедиться что тесты проходят (`pnpm test`).
2. **Разобрать Paloma вживую** (она установлена на этой машине). Пройти по всем экранам,
   которые относятся к баням, и собрать:
   - карту модулей и экранов, навигацию, терминологию (как называются сущности);
   - роли и права доступа — что видит и может кассир / администратор / владелец;
   - потоки: приём гостя, расчёт по времени, выбор помещения, оплата, смена, Z-отчёт,
     возврат, работа с абонементами, склад, настройки заведения и филиалов;
   - как именно выглядит тарификация времени и доплата за гостей (если есть);
   - скриншоты ключевых экранов в `docs/paloma/` (папка в репозитории).
3. **Написать документ** `docs/paloma-razbor.md` (или `.html` в стиле остальных docs):
   таблица «Paloma / у нас / называется иначе / поток отличается» по срезу «только бани»,
   с выводами — что дозабрать, что переименовать, где поменять поток.
4. **Дать документ на согласование заказчику** перед тем как писать код.
5. **После согласования — реализовать Фазы 0→1→2** по плану выше, через TDD, каждую фазу
   отдельной веткой и PR. Фазу 3 — по решению о филиалах. Фазу 4 не трогать без решений
   по ОФД и хостингу.

Правила проекта, которые нельзя нарушать (из README и памяти):
- `org_id` только из подписанного токена, никогда из тела запроса.
- Цену считает только `packages/core/src/pricing.ts` — не дублировать расчёт в интерфейсе.
- Один клиент `pg` не работает параллельно — внутри `withTenant` идти последовательно.
- Отдельной «таблицы выручки» нет намеренно — отчёты считаются из заказов, позиций,
  платежей.
- Справочники не удаляются, а архивируются (`archived_at`).
- Деньги — целые тиыны, append-only: платёж/списание не редактируется, только обратной
  операцией. Закрытая смена не правится.
- Все контролы — только shadcn/ui, цвет только через токены в `:root` + `@theme inline`.
- Не пересоздавать базу молча, если у заказчика открыта страница кассы/кабинета.
