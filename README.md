# SaaS для бань, саун и развлекательных центров

Мультитенантная ERP/POS-платформа. Реализовано ядро MVP: касса со сменами и таймером,
бронирование, абонементы, товары, расчёт и оплата, кабинет владельца с аналитикой.

Техническое задание — в [docs/](docs/): [ТЗ MVP](docs/tz-mvp.html) и
[версия простыми словами](docs/tz-prostoe.html).

## Запуск

Нужны Node 22.6+ (проект работает на Node 25) и PostgreSQL 14+.

```bash
pnpm install
cp .env.example .env

createdb sauna_dev
psql -d sauna_dev -c "CREATE EXTENSION IF NOT EXISTS btree_gist; CREATE EXTENSION IF NOT EXISTS pgcrypto;"

pnpm db:reset      # миграции, справочники и месяц демо-истории
pnpm dev           # API :3001, касса :5173, кабинет :5174
```

| Что | Адрес | Вход |
|---|---|---|
| Касса | http://localhost:5173 | привязать кассу: `+77010000001` / `owner123`, дальше PIN `1234` |
| Кабинет владельца | http://localhost:5174 | `+77010000001` / `owner123` |

Касса при первом запуске просит привязку к филиалу — это делает руководитель один раз.
Дальше сотрудники входят по PIN: `1234` — кассир, `1111` — владелец. Украденное
устройство отзывается в один запрос, после чего его PIN перестаёт работать.

`pnpm db:reset --no-history` создаёт базу без демо-истории — для чистого старта.

## Проверка

```bash
pnpm stop        # остановить всё, если порты заняты после прошлого запуска
pnpm test        # 86 тестов: вход, тарификация, день кассира, абонементы, отчёты
pnpm test:unit   # только доменное ядро, без базы
```

`pnpm test` пересоздаёт базу `sauna_dev` перед каждым набором — не запускайте на базе
с нужными данными. Наборы идут по очереди: они делят одну базу, и параллельный прогон
ловил бы чужие смены.

## Что работает

**Вход на кассу** — устройство привязывается к филиалу руководителем один раз, дальше
сотрудник входит четырьмя цифрами. PIN без привязанного устройства бесполезен, привязка
без PIN — тоже. Экран рассчитан на палец, мышь и физическую клавиатуру.

**Изоляция организаций** — Row-Level Security. Без контекста организации данных не
видно вообще, запись в чужую организацию отклоняет СУБД, хеш пароля роли приложения
недоступен даже на чтение: пароль сверяется внутри базы.

**Смены и касса** — открытие с суммой в ящике, движения наличных, закрытие со сверкой
и неизменяемым Z-отчётом. Закрытую смену править нельзя.

**Визиты и таймер** — старт с брони или без, продление с предупреждением о следующей
броне, доп. услуги и товары, расчёт по факту. Таймер считается от серверного времени.

**Тарификация** — правила по дню недели и времени суток, посегментный расчёт при
переходе через тарифную границу, минимальная длительность, шаг округления с льготными
минутами. Считает один сервис, к нему ходят и касса, и бронирование, и отчёты.

**Бронирование** — шахматка по дню, непересечение гарантирует ограничение `EXCLUDE`
в PostgreSQL с учётом времени на уборку.

**Абонементы** — по посещениям, по часам, безлимит на срок. Баланс — свёртка
append-only леджера, а не редактируемое поле. Заморозка хранится интервалом и сдвигает
срок вычисляемо. Система сама предлагает подходящий абонемент при расчёте; частичное
покрытие считается по тарифным сегментам, остаток гость доплачивает.

**Деньги** — целые тиыны, снимок цены в каждой позиции, идемпотентные платежи,
append-only: платёж нельзя изменить или удалить даже напрямую в базе. Возврат —
обратная операция со ссылкой на оригинал.

**Кабинет владельца** — выручка с динамикой, средний чек, загрузка по дням недели и
часам, продажи по видам и позициям, смены с расхождениями по кассе, абонементы
с остатком обязательств перед гостями. Светлая и тёмная темы.

## Интерфейс

React 19 + Vite. Готовые компоненты — [shadcn/ui](https://ui.shadcn.com) поверх Radix:
Select, Dialog, Tabs, Button, Input, Label. Они лежат в `src/ui/` как обычный код проекта,
правятся напрямую, добавляются через `pnpm dlx shadcn@latest add <имя>`.

**Цвет объявлен один раз.** Палитра живёт в `:root` в `styles.css`, а блок `@theme inline`
над ней пробрасывает те же переменные в Tailwind и shadcn. Поэтому `bg-primary` в
shadcn-компоненте и `var(--accent)` в своём CSS — это буквально одно значение, и тёмная
тема кабинета работает для готовых компонентов без отдельной настройки.

Не пишите цвета значениями в компонентах: добавьте токен в `:root` и, если он нужен
shadcn, строку в `@theme inline`.

Размеры под палец задаются классом на месте использования (`h-11`, `h-12!`). Восклицательный
знак нужен там, где у shadcn своя высота через `data-[size=...]` — обычный класс её не перебьёт.

## Работа без интернета

Касса переживает обрыв связи. Что при этом происходит:

| Что делает кассир | Без связи |
|---|---|
| Смотрит зал, таймеры идут | работает — из последнего снимка |
| Открывает карточку визита | работает — карточки активных визитов подгружаются заранее |
| Добавляет товар, продлевает, рассчитывает | копится в очереди |
| Принимает наличные | копится в очереди |
| Оформляет бронь | **нельзя** — программа не проверит занятость на других кассах |
| Списывает абонемент | **нельзя** — нужен актуальный остаток |
| Принимает карту | **нельзя** — терминал сам требует связь |

Наверху кассы видно «Нет связи · N операций ждут». Когда интернет возвращается,
очередь уходит сама, по порядку.

**Почему повтор безопасен.** Каждая изменяющая операция уходит с ключом
идемпотентности. Сервер занимает ключ до выполнения — поэтому даже два
одновременных повтора выполнятся один раз, а второй получит готовый ответ.
Это проверено тестами в `apps/api/test/offline.test.ts`, включая гонку.

## Два способа поставить кассу

**Как приложение из браузера (PWA).** Открыть адрес кассы, в браузере выбрать
«Установить». Появится ярлык, окно без адресной строки, работа без интернета.
Ничего собирать не нужно — это та же сборка, что и сайт.

**Как программу для Windows или macOS (Tauri).** Нужна для прямого доступа
к чековому принтеру и фискальному аппарату.

```
# один раз на машине разработчика
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh

pnpm --filter @sauna/pos app:dev      # запуск в окне программы
pnpm --filter @sauna/pos app:build    # сборка под текущую систему
```

Tauri собирает **только под ту систему, где запущен**: на Mac получится `.dmg`,
а `.exe` для касс собирается в GitHub Actions — `.github/workflows/app.yml`,
запускается тегом `app-v*` или вручную.

В приложении адрес сервера задаётся на экране привязки кассы: страница лежит
внутри программы и не знает, куда обращаться.

## Переменная `JWT_SECRET`

Токены сессии подписываются секретом из `JWT_SECRET`. В разработке можно не задавать —
подставляется `dev-secret-change-me` из `.env.example`. На сервере это запрещено: если
`NODE_ENV=production`, а `JWT_SECRET` не задан или равен значению по умолчанию, сервер
не запускается. Перед выкладкой задайте случайную строку от 32 символов, например:

```bash
openssl rand -hex 32
```

## Решения, которые стоит знать до правок

- `org_id` берётся только из подписанного токена, из тела запроса — никогда.
- Цену считает `packages/core/src/pricing.ts`. Не дублируйте расчёт в интерфейсе:
  разойдётся с отчётами.
- Один клиент `pg` не выполняет запросы параллельно — внутри `withTenant` идите
  последовательно, без `Promise.all`.
- Отчёты считаются из заказов, позиций и платежей. Отдельной «таблицы выручки» нет
  намеренно: два источника правды разойдутся. Осторожно с соединениями — заказ
  с двумя платежами удваивает строки визита, если считать всё одним запросом.
- Справочники не удаляются, а архивируются (`archived_at`).
- Миграции идут под владельцем базы (он обходит RLS), приложение ходит ролью
  `sauna_app`, на которую политики действуют.
